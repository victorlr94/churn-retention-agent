# ADR-0007 — Observabilidad: log JSONL de sesiones con estimacion de coste

| Campo       | Valor                  |
|-------------|------------------------|
| Estado      | Aceptado               |
| Fecha       | 2026-06-23             |
| Autor       | victorlr94             |

## Contexto

Cada llamada al agente consume tokens del LLM (Claude Haiku 4.5) y tiene una
latencia observable. Sin instrumentacion, no hay forma de responder a: ¿cuanto
cuesta una sesion tipica? ¿que fraccion activa HITL? ¿que tier se recomienda
con mas frecuencia? Estas preguntas son clave para operar el sistema y para
demostrar responsabilidad economica en un portafolio.

## Opciones consideradas

| Opcion | Pros | Contras |
|--------|------|---------|
| **JSONL append-only** (elegida) | Sin dependencias externas; legible con cualquier editor; append-only es crash-safe; facil de filtrar con jq/Python | No es real-time; no sirve para sistemas de alta concurrencia |
| OpenTelemetry (OTEL) | Estandar industrial; se integra con Jaeger/Grafana | Requiere colector externo; sobrecosto para un POC de portafolio |
| SQLite | Queries SQL; persistente y estructurado | Requiere esquema, migraciones; excesivo para el volumen esperado |
| LangSmith tracing | Especifico para LangChain; dashboards listos | Dependencia de servicio externo; no aplica a produccion general |

## Decision

Implementar un `ObservabilityStore` con backend JSONL (`logs/sessions.jsonl`,
gitignoreado). Cada sesion del agente escribe una linea JSON atomica con:
session_id, customer_id, fase, latencia, propension, cltv, ev, tier, flags
HITL/security y estimacion de coste.

La estimacion de coste usa Claude Haiku 4.5 como modelo de referencia ($0.80/1M
input tokens, $4.00/1M output tokens) con la heuristica de ~4 chars/token.
No es exacta, pero es suficiente para comparaciones relativas y detectar outliers.

El store opera en modo **no-op** cuando `log_path=None`, lo que permite usarlo
en tests sin efectos secundarios y en modo degradado si el sistema de ficheros
no esta disponible.

El endpoint `GET /api/v1/metrics` expone las metricas agregadas (total de sesiones,
latencia media, tasa HITL, tasa bloqueados, distribucion de tiers, coste estimado)
para integraciones externas. El script `scripts/show_sessions.py` permite consulta
desde la linea de comandos.

## Consecuencias

**Positivas:**
- Visibilidad inmediata sobre coste y comportamiento del agente en produccion.
- Sin dependencias externas adicionales.
- Log legible por humanos; facil de inspeccionar o procesar con jq.
- Modo no-op preserva la suite de tests existente sin cambios.

**Negativas:**
- La estimacion de coste es una aproximacion (~4 chars/token); no es facturada.
- No hay soporte para busqueda por rango de fechas ni indices; solo lectura secuencial.
- Si el sistema escala a miles de sesiones/hora, habria que migrar a SQLite o OTEL.

## Migracion futura

Si el volumen de sesiones lo justifica: `ObservabilityStore` es una clase con una
interfaz clara (`record`, `load_all`, `compute_metrics`); sustituir el backend
JSONL por SQLite o enviar a OTEL requiere solo reimplementar esos tres metodos
sin tocar los callers.
