# ADR-0006: Estrategia de evaluación del agente

**Estado:** Aceptado
**Fecha:** 2026-06-23
**Contexto:** Fase 5 — Evaluación del agente de retención

---

## Contexto

El agente (LangGraph ReAct + Claude Haiku) tiene componentes deterministas
(EV = P·uplift·CLTV − costo, HITL threshold, guardrails de injection) y uno
no determinista (el LLM). Necesitamos un gate de CI que:

1. Verifique la corrección del sistema completo end-to-end.
2. No requiera ANTHROPIC_API_KEY, modelo pkl ni CSV en CI.
3. Sea determinista y reproducible en cualquier entorno.
4. Falle con exit code 1 si la calidad cae por debajo de umbrales definidos.

---

## Decisión

Evaluación con **componentes fake inyectables** que implementan los mismos
contratos (Protocol) que los componentes reales:

| Componente real | Fake de evaluación |
|-----------------|--------------------|
| `LightGBMChurnModel` | `FakeChurnModel(propensity=X)` — Protocol ChurnModel |
| `ChatAnthropic` | `StatefulFakeLLM` — `BaseChatModel` con loop ReAct simulado |
| Dataset CSV | `make_fake_data(customer_id, cltv)` — DataFrame mínimo |

La `StatefulFakeLLM` inspecciona el historial de mensajes para decidir qué
tool call emitir (query_propensity → select_best_offer → mensaje final),
reproduciendo el ReAct loop del agente real sin ninguna llamada de red.

**Suite de 5 casos** cubriendo las cuatro rutas del grafo:
- EV bajo → LIGHT, sin HITL
- EV medio → STANDARD, sin HITL
- EV alto → PREMIUM, HITL aprobado
- EV alto → PREMIUM, HITL rechazado
- customer_id con injection → bloqueado

**Métricas y umbrales del gate:**

| Métrica | Umbral | Justificación |
|---------|--------|---------------|
| `pass_rate` | ≥ 80% | Permite fallos únicos en el suite de 5 |
| `tier_accuracy` | ≥ 80% | Corrección económica mínima aceptable |
| `hitl_recall` | = 100% | HITL debe dispararse siempre que se requiera |
| `block_rate` | = 100% | Seguridad: injection jamás debe pasar |

Los umbrales de seguridad (`hitl_recall`, `block_rate`) son 100% porque son
invariantes del sistema, no heurísticas. Una bajada indica un cambio de
comportamiento, no ruido.

---

## Alternativas descartadas

### A. Evaluación con LLM real en CI

Requiere ANTHROPIC_API_KEY como secret en CI, añade latencia (~10-30s por caso)
y coste por ejecución. El LLM real añade no-determinismo: el mismo caso puede
pasar unas veces y fallar otras. Descartado por complejidad operacional y coste.

### B. Tests de golden outputs con snapshots

Comparar la respuesta de texto del agente con un snapshot guardado. Frágil ante
cambios de prompt y modelo (cualquier reformateo del LLM rompe el test). No
captura errores de EV ni de HITL. Descartado por fragilidad.

### C. Evaluación con framework externo (RAGAS, DeepEval)

Los frameworks de evaluación de RAG/agentes (RAGAS, DeepEval, Langsmith Evals)
están orientados a calidad semántica de respuestas, no a corrección económica o
lógica de grafos. Añaden dependencias pesadas para lo que necesitamos. El dominio
(EV, HITL threshold) tiene respuestas correctas conocidas → evaluación rule-based
es suficiente. Descartado por overhead sin beneficio claro.

---

## Consecuencias

**Positivo:**
- Gate de CI completamente autónomo: sin secretos, sin red, sin artefactos pesados.
- Tests deterministas (los mismos inputs producen los mismos outputs siempre).
- La `StatefulFakeLLM` valida el flujo completo del grafo, incluyendo ToolNode.
- Cobertura de las cuatro rutas del grafo en ≈ 5 segundos en CI.

**Negativo:**
- No evalúa la calidad semántica del mensaje final del LLM.
- La `StatefulFakeLLM` no cubre el caso de LLM que llama tools en orden incorrecto
  o que no llama tools en absoluto (eso requeriría el LLM real).
- Ampliar la suite requiere calcular manualmente los EVs esperados.

**Evolución futura (Fase 6 stretch):**
- Añadir eval con LLM real opcionalmente (`--real-llm` flag) para correr
  fuera de CI con ANTHROPIC_API_KEY cuando se cambia el prompt.
- Añadir métricas de calidad semántica (coherencia de la recomendación) con
  un LLM-as-judge de bajo coste (Claude Haiku).
