# ADR-0005 — Framework de API REST: FastAPI

| Campo       | Valor                          |
|-------------|--------------------------------|
| Estado      | Aceptado                       |
| Fecha       | 2026-06-23                     |
| Autores     | Victor Manuel Lugo Ramirez     |

## Contexto

La Fase 4 expone el agente de retención como servicio HTTP para que otras
herramientas (UIs, sistemas CRM, CI) puedan invocarlo sin correr el CLI.
El servicio debe:
1. Manejar el HITL en dos pasos (analyze → approve).
2. Documentar la API automáticamente (OpenAPI).
3. Validar inputs/outputs con tipos estrictos.
4. Ser async-friendly para no bloquear el event loop durante el `invoke` del grafo.

## Opciones evaluadas

| Opción | Ventajas | Desventajas |
|--------|----------|-------------|
| **FastAPI** | Pydantic nativo; OpenAPI auto-generado; async de primera clase; TestClient sin server real | Más dependencias que Flask |
| Flask | Mínimas dependencias; familiar | Sin validación de tipos nativa; sin async nativo |
| Django REST Framework | Admin + Auth out-of-box | Overhead masivo para un servicio de un agente |

## Decisión

**FastAPI** por las siguientes razones:

1. **Pydantic nativo**: los schemas de request/response son los mismos modelos
   que usan las capas internas — sin doble definición.
2. **OpenAPI automático** (`/docs`): el swagger documenta la API sin esfuerzo.
   Importante para un portafolio que quiere demostrar API bien diseñada.
3. **TestClient sin servidor**: los tests de la API no levantan un proceso — son
   unitarios aunque ejerzan el stack completo de HTTP/routing.
4. **Dependency Injection**: `Depends(get_compiled_graph)` desacopla el grafo
   de los endpoints y permite overrides en tests con una línea.
5. **Lifespan context**: carga del modelo una sola vez al arrancar, no en cada
   request.

## Flujo HITL en REST

```
POST /api/v1/customers/{id}/analyze
  → status: "pending_approval", session_id: "uuid"

POST /api/v1/sessions/{session_id}/approve
  → body: {"approved": true}
  → status: "completed", decision: {...}
```

El `session_id` es el `thread_id` del checkpointer `MemorySaver` de LangGraph.
El estado persiste en memoria entre las dos llamadas.

## Consecuencias

- **Positivo**: `/docs` documenta los endpoints automáticamente para quien revise el portafolio.
- **Positivo**: los tests de la API son rápidos (sin I/O de red).
- **Negativo**: `MemorySaver` no persiste entre reinicios del servidor. Para producción
  se reemplazaría por `SqliteSaver` o `PostgresSaver`.
- **Negativo**: `invoke()` es síncrono; en producción se usaría `ainvoke()` con `async def`.
